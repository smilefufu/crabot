# 项目上下文维护

## 工作流程

1. 读取并遵守项目根目录已有的 `AGENTS.md` 或其链接指向的正文；已有项目约定和用户明确要求优先，不用通用模板覆盖。
2. 根据当前任务实际需要读取职责明确的现有文档：
   - 从 `README.md` 了解项目入口、运行方式和简短概览；
   - 从 `ARCHITECTURE.md` 了解组件边界、关键数据流、状态机和跨模块不变量；
   - 从项目已有的决策目录了解已经生效或被取代的决定；
   - 按任务读取协议、运行手册、贡献指南、设计文档和领域文档。
3. 先确认项目现有的目录和权威来源，不要根据文件名、旧计划或历史报告自行推断当前事实。
4. 发现长期项目事实、架构说明或引用缺失、过时、互相矛盾时，向主控说明具体缺口和证据。
5. 持续开发代码项目且规则正文缺失时，在首次业务修改前创建最小 `AGENTS.md`；其余一般文档修改按主控交办范围进行。创建或修改后主动重读，并报告可核实的结果。

## 初始化与 Git 纪律

- 只读调查、问答和一次性文件处理不初始化项目。开发任务开始前确认实际 workspace；要改到另一仓库或新 worktree 时先交主控重新安排，不把临时 cd 当作基线已切换。
- 创建 AGENTS 前读取已有项目说明，只写规则、文档入口、已确认命令及适用的 Git 约定。未知信息暂缺，排他创建失败时重读现有文件。只有 CLAUDE 正文时沿用，不再生成另一份正文。
- README 随实际入口、运行和验证方式形成而维护；架构文档与决策记录遵循既有职责，不预建空文档集。
- 使用 Harness 给出的 Git 观察；初始化、提交及分支类操作前后，通过只读工具 inspect_workspace_git 刷新核实。检测失败先排障，再做依赖版本基线的业务修改；检测结果只是当时事实，不证明没有并发写入。
- 无仓库或尚无首个提交时，先明确仓库归属、排除不应入仓的文件，再由主线建立初始提交；老项目在改业务代码前保存原有源码基线。父仓库忽略了 workspace 时先报告处理，不自动建立嵌套仓库。
- 保护已有暂存和未提交改动。并行独立开发优先使用预先准备的 worktree；同一工作区的提交由主线负责，不能混入或清理别人的工作。
- 有意义的改动通过相关验证和完整 diff review 后，默认本地提交本任务范围；提交前检查暂存区，避免无范围暂存。需要中断或切换时按项目约定保存本任务 WIP，明确未完成的验证。
- 项目禁止自动提交时遵循其约定；缺 Git、身份、签名或 hook 失败时报告真实错误，不伪造身份、不关闭保护。push、PR 和 merge 遵循项目流程及用户授权。
- 交付包含实际提交 hash、验证结果和剩余改动。没有改动不造空提交；干净、HEAD 变化或 WIP 均不能证明任务完成。

## 新建 AGENTS 的最小默认正文

已有文件不套用本模板。新建时按已确认事实补充现有文档入口和运行/验证命令，删除不适用条款，不填未验证内容。

```markdown
# 项目规则

## 文档与验证

- 按任务读取现有 README、架构、协议和决策文档，先确认当前权威来源。
- 只维护已确认的长期规则与事实；任务日志、进度和猜测不写入本文件。
- 修改后运行相关验证并审查 diff，按实际证据报告结果。

## 版本管理

- 修改前确认实际仓库、分支和已有改动；在 Crabot 中使用 Harness 的 Git 检测并在关键操作前后刷新，其他执行环境使用 Git 等价检查。
- 未建立版本基线时先初始化并提交必要基础文件；老项目先保存原有源码，已有其他版本管理约定时沿用。
- 保留已有暂存和未提交工作，只提交本任务范围；并行开发优先隔离 worktree，同一工作区由主线负责提交。
- 有意义的改动验证和审查通过后本地提交；需要保存未完成工作时明确标记 WIP。初始化、必要提交或检测失败先处理，不伪报成功。
- 发布遵循用户授权和项目流程；报告实际提交、验证结果和剩余改动。
```

## 边界

- 只在上述开发条件下补建缺失规则；不创建混合当前任务状态、项目事实、决策和交接内容的上下文文档。
- 不创建、修改、取代或迁移决策记录。执行过程中出现可能影响长期项目工作的决定时，把事实和建议报告给主控，由主控判断并管理决策文档。
- 不把执行日志、命令输出、临时阻塞或当前任务进度写入长期项目文档。
- 不要求每个任务都修改文档；没有长期文档变化时直接完成任务，不输出“无需更新文档”之类的仪式性说明。
- 不把旧报告、历史计划或名称含 `latest` 的文件直接当成当前权威，除非项目规则或当前文档明确指定。
