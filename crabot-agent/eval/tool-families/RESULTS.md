输出 token、缓存与实际请求并行方式均未计入，这只是成本敏感性说明，不是实际 token 结论。

### 可比场景的成本

仅汇总两版均达到目标且无非法调用参数的 4 个场景：三项记忆、Schedule、网页委派、外部两项读取。

| 指标 | 旧版 | 新版 | 变化 |
|---|---:|---:|---:|
| LLM 请求 | 14 | 12 | -2 |
| 发现调用 | 6 | 5 | -1 |
| 总输入 token（含缓存） | 78,132 | 70,169 | -10.2% |
| 输出 token | 2,227 | 2,319 | +4.1% |
| 输入加输出 token | 80,359 | 72,488 | -9.8% |
| 累计请求耗时 | 69.979 秒 | 62.580 秒 | -10.6% |

耗时只加每次 Provider 请求，不含人工检查/夹具修正暂停，也不是线上消息端到端延迟。
缓存受调用顺序和共享前缀影响，输入总量不是收费金额。本次每场景每版仅一次，以上变化不具统计显著性。

### 夹具修正与结果边界

首批 37 次请求中，4 条轨迹因夹具不支持合法的记忆搜索/任务板读取提前停止。
补齐模拟结果后，从尚未发送给模型的工具结果处继续，保留已发送的请求、响应和全部 usage；
其中两条随后走到记忆目录/任务板创建，再补齐后续接。共补发 11 请求，未重抽样或修改原场景。
`resume_fixture` 事件明确记录续接边界；最终所有轨迹均自然结束、达到目标或触及原 7 轮上限。

两个夹具缺陷保留原记录并披露：

- 初次记忆搜索模拟行的 status 写成了协议外的 active，已在脚本改为 confirmed；模型轨迹未重跑。
  这不影响本次所核对的工具名、ID 和更新参数，但进一步限制了结论：不能把对照当作完整 Memory 业务验收。
- 旧版 MCP 轨迹的模拟任务板目标 ID 为 objective-fixture，不符合 UUID schema，后续建项复用了该 ID。
  脚本现已改用合法合成 UUID，并做本地 schema 检查；本次旧结果保持原样、整对排除收益汇总。

所有业务结果为合成值；模型仅选择工具，没有验证真实服务权限、持久化、副作用、错误恢复或 Worker 完成质量。
代码尚未部署，没有候选线上总体收益结论。

### 对原改造预期的判断

内置工具按族获取、完整可见和外部 MCP 搜索分离符合预期；模型确实能直接选对内置族。
同族多步有收益：记忆三项请求数减半，输入 token 下降 41.1%。内置搜索误判在两个读取案例中得到改善。
“普遍减少步骤或 token”未成立：Schedule 没有少轮次，已知外部服务先列目录的选择还增加一轮及 56.3% 输入。
本次无需改动已确认的加载契约；已知服务直接加载的选择效率可作为后续提示/说明优化观察项，不能静默改成另一套加载行为。
