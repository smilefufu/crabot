# Manager 答复投递与收尾修复验证

## 范围与结论

2026-09-21，保留精简核心和 15 项普通 Manager 工具，修复两个已确认的迁移遗漏：

- Manager 的 `send_message` 已移除 `intent` 参数，却仍沿用 `ask_human / waiting_human` 和旧 loop 描述。改为符合实际接口的独立说明。
- 普通答复的投递责任和收尾要求在核心精简时被弱化。恢复“用工具投递答复，普通文本不外发；能推进就继续，否则结束，不轮询或重复发送”，核心保持 299 字（去除空白）。为保持原 300 字限制，只压缩其它等义措辞，保留授权、任务板、文档、记忆、验收、投递范围及外部输入边界。

没有增加工具、修改 adapter、改变结束状态机或依靠新的强制截断。

## 首版失败证据

只修工具说明的第一批 Kimi 合成验证：2 条轨迹、4 次请求。一条发送一次后结束，另一条直接输出内部文本，在收到现有一次性交付提醒后仍未调用投递工具。

随后把同一批原响应接入真实 `ManagerLoop` 重放，失败轨迹结束后 `pendingReply=true`、成功发送数为 0；成功轨迹为 1 次发送、`pendingReply=false`。没有重抽样，不能把第一批当成验收通过。

## 完整循环验收

用户批准上限 12 次；实际只用 6 次，全部成功返回。目的端为 `https://api.kimi.com/coding`，模型 `k3`，每次最多 4096 输出 token，`thinking.level=high` 经当前产品 adapter 映射。无自动重试。

使用真实 ManagerLoop、SessionStore、共享 Engine、当前构建的核心及工具定义、当前产品 adapter。入站消息是虚构的“17 × 23 等于多少？”，由产品渲染为真实 Channel 入站格式；投递 handler 仅记录内存 outbox 并返回合成平台回执，不联系真实 Channel，不使用生产历史、图片或其它业务工具。

| 轨迹 | 真实 Kimi 请求数 | 观察结果 |
|---|---:|---|
| 正常问答 A | 2 | 第一次调用 send_message 发送 391；成功后返回 end_turn，无工具调用 |
| 正常问答 B | 2 | 第一次调用 send_message 发送 391；成功后返回 end_turn，无工具调用 |
| 重复发送被拒 | 1 | 既有成功投递后，真实 Engine 拦截相同参数的第二次调用；Kimi 收到错误后立即 end_turn，无工具调用 |
| 空内容被拒 | 1 | 既有成功投递后，模拟空内容失败；Kimi 收到错误后立即 end_turn，无工具调用 |

两个错误案例的前两次 assistant 工具调用由固定脚本构造，经过真实 Manager/Engine 执行，随后才调用 Kimi；不冒充模型自行产生这两次前置调用。重复拒绝由产品现有护栏产生；空内容错误由模拟 handler 产生，本次没有实现或验证生产空内容校验。

错误回执已在紧接着的实际请求中核对：`is_error=true`，分别包含“禁止重复发送消息。如无其他事，则立即结束本回合。”和“消息内容不能为空。如无其他事，则立即结束本回合。”。

四条轨迹均实际完成，outbox 恰好 1 条，待回复义务已清除；最后响应均为 `end_turn` 且无工具调用。后续内部文本未被外发。两种拒绝后的模型均未换词重发，也未再尝试同参数调用。

本地复现测试先失败；最终角色提示词、guidance、工具面和 Manager loop 四文件 213 项通过，Agent 构建通过。实测前后源码 SHA-256 相同。

## 限制与后续

这是短合成上下文上的有限验收，未重放原事故约 70 万 token 的历史，不能证明所有生产会话都不再重复，也不能据此把 adapter 保真缺陷排除为其它场景的影响因素。已确认的说明冲突与核心语义遗漏已修复；根因的贡献比例不作推断。

原始请求、响应、账本及脚本保留在执行机临时验收目录 `kimi-manager-loop-validation`，未提交凭据或生产数据。发布和部署状态在交付对话中报告。
