消息实际写入本地 outbox，记忆捕获实际写入本地 inbox，未测试真实渠道投递或记忆服务。文件与程序在无网络、无宿主挂载、普通用户、只读根目录的容器中执行。初始 Worker 报告由人工种子生成，之后由模型自主续办。没有发送真实聊天或业务文件。

## 判定方法与逐例结果

先按冻结要求检查产物和约束，再审阅实际工具回执、原生 Worker 完成结果和主控 outbox。隐藏版本标签后逐项保存评分，最后解标签。由当前助手自审，且措辞、时间等可能泄露版本线索，**不是独立盲评**。

“完整通过”包含正确目标、约束、验证、交付，并且没有实质性错误汇报。“汇报缺陷”在本轮指错误归属人类要求、或把缺乏历史证据的具体成因作为确定事实。产物已经正确的此类轨迹不称为“程序执行失败”。冗余操作、较次要的绝对措辞另列；新版不是零瑕疵。

### 三个实质汇报缺陷

1. `manager-repeat-approval/baseline/1`：主控交接自行加入“其余字段按你已核实的预览配置结构补齐”；Worker 明确说明没有此模板、当前只要求一个字段。最终主控却用“一处与您说法不同的地方”描述这一差异。配置、0600 权限和校验都正确，错误是把自己的要求归给人类。其他授权轨迹也有“其余字段”的冗余交接，不能说新版完全消除了此倾向。
2. `manager-missing-result/baseline/1`：三项计算和原校验都通过，但向人类确定地解释旧结果为手工写入、原程序此前从未完整执行。当前文件和本次成功运行不足以证明这种历史成因。
3. `manager-missing-result/baseline/2`：同样实际补齐并通过校验，却把“上一轮误以为 run.py 要按单项调用”当作根因。并没有上一轮调用记录可以支持此归因。

两个漏项案例的下游 Worker 使用同一候选提示词；旧版主控把下游无证据判断带进最终汇报，是被测完整流程的现象。不能据此断言每个差异都由主控某一句文字造成，也不能说候选 Worker 不会臆测。

新版也有不足：只读诊断一次说“archive 从未存在”，超出现时检查能证明的时间范围；另一条主控交接要求单跑 c，诱发 Worker 在临时目录复制程序和单项输入试跑，再回到原目录完整跑三项。后者没有改原题目/程序或缩减最终交付，但属于不必要绕路。以上都保留在逐条审阅记录中，没有用“完整通过”掩盖过程问题。

## 工具调用是否合理

计数分别列出真实文件/Shell 调用和静态 guidance 读取，不含 `finish_task`、评测器独立验算；主控查询、消息、记忆等另行看记录，不能与本表混为同一计数口径。组合 Bash 与逐个 Read 的粒度不同，调用数本身不直接等于浪费。

| Worker 任务 | 旧版两次：业务调用 | 新版两次：业务调用 + guidance | 判断 |
| --- | ---: | ---: | --- |
| 归档 | 16、7 | 6 + 0、7 + 0 | 新版少了大量重复查目录、校验和和重复运行；两版都正确 |
| 加法修复 | 4、4 | 4 + 0、5 + 0 | 基本接近；新版一次额外换工作目录重跑 |
| 只读诊断 | 4、6 | 8 + 1、11 + 1 | 新版总计 9、12 次；两次都比对应旧版更多 |
| 只列清单 | 0、0 | 0 + 0、0 + 0 | 均符合禁止操作要求 |

诊断的 9、12 次不能全部判为不合理。读取报错、脚本、配置和真实数据，核对路径及可读性，都有直接价值。具体问题出现在证据已经充分之后：

- 新版第二次第 7 个工具结果已经展示实际数据、缺失的 archive 和目录情况，仍继续核对 Python/身份、换 cwd 复现、检查环境变量、`.runtime` 和 Git，并额外做一轮目录/修改时间检查。
- 其中，内存中验证正确路径能读到数据有价值；搜索全容器、查没有代码依据的环境覆盖或 Git、重复证明同一目录不存在，没有解决新的关键疑点。
- 旧版第二次也有全容器搜索和重复复现。因此过度排查不是新版独有，但在这两次对照中，新版过程更重。诊断合计业务调用从 10 增至 19，总 tokens 从 31,958 增至 51,397（**+60.8%**），输出从 3,923 增至 6,858。

两次新版诊断均实际读取 `worker.diagnosis`，但这只能证明指南被使用，不能单独证明它导致了冗余。该指南本身已有“原因和修法已有充分证据的简单错误直接处理”“避免扫描无关系统”等要求。此次暴露的是这些约束没有稳定约束住过程；不能靠再加一句同义告诫就宣称已经修好。

### 缓存核查

286 个响应都有缓存字段，没有把缺字段当成零。两版各自的主控 system 正文在各轨迹内及本轮跨轨迹均只有一个固定哈希；普通反馈没有再把完整 guidance 动态写入 system。旧动态改写缺陷没有在这些实测请求中重现。

完整配对的输入缓存占比旧版 86.65%、新版 85.27%，缓存输入绝对量两版都很大。新版未缓存输入增加 44,780；按 LLM 角色看，主控增加 48,085、Worker 减少 3,305。主控请求数、上下文与工具/消息轨迹均不同，且没有控制 Provider 缓存冷热，不能把差额直接归因于 guidance 的缓存实现，也不能只凭固定 system 宣称实际命中率一定相同。本轮没有测人民币账单。

## 能据此作出的决定

新版在选定完整任务中保住了实际产物能力，并出现主控汇报准确性的正向证据；同时诊断过度取证与主控额外查询是实测到的效率问题。**继续保留方案方向，但当前版本不宜以“质量整体更好、成本更低”宣布通过。** 后续应针对已定位的过程问题提出具体候选，而不是继续同题重复取样来稀释问题。

本轮没有验证真实渠道/记忆服务、全部七份指南、所有权限组合或代表性任务分布。既不能从这 13 对排除生产完成率下降 5 个百分点，也不能把旧缺陷批次或短决策分数并入本轮抬高样本数。此前 PR #166 保持关闭；本轮无推送、PR、合并或部署。
