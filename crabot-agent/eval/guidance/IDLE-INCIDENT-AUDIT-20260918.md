最后一项是评测应保留的隔离边界；模型、工具装配、实际历史及连续性则必须在事故复现中对齐。Docker 的真实文件/命令执行不能弥补这些输入差异。此前“已问过的阻塞”案例也只模拟询问交付时间，不含连续自省报告的历史。

本批“完整执行”指单个案例继续跑到运行收口，不代表连续多次自省的长期会话回放。两版各 3 次未外发只能说明人工案例里的结果，不能用于验证这两次线上事故的修复，也不能据此判断事故为随机错误。

实际 Agent 进程从主仓 `crabot-agent` 目录加载 dist，2026-09-17 23:34 启动；guidance、核心提示词与 loop 的构建文件均生成于 23:32。加载路径中的任务板指南仍为基础版“持续跟进与长期记录”，不是未发布的增量“任务自省”稿。

基础版写明“同一阻塞已单独说明且没有变化，不再提醒”，结尾是“无新增信息时可直接收口”，没有明确排除检查完成报告或无变化状态汇报。两次外发都在报告“自省完成”，第二次还同时声称“不重复发送阻塞提醒”。行为说明仅约束“阻塞提醒”不足以稳定表达全部自省对外输出边界；尚未证明模型选择发送的唯一原因，也不能归因于某一条历史消息。

增量稿已有“自省过程、检查完成及无变化的状态不对外发送”“没有需要人类介入的新情况时内部结束，不发送自省报告”，但其线上适用性仍待验证，不能将本次基础版事故称为增量部署后复发。
