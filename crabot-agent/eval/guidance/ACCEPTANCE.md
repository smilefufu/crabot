# 核心提示词与 Guidance：分阶段质量验收

2026-09-17，用户同意继续按“结构简化，同时交付质量没有明显下降”的方向验证。保持已确认核心和七份 guidance 不变，不根据个别输出补措辞。本文件先冻结评价口径，再产生新模型输出。

**当前状态：装配缺陷已本地修复，整体质量验收仍未完成，尚未新增模型比较。** 第一阶段旧运行中的候选改写了 system prompt 与缓存标识，该批数据仍只记录有缺陷的实现，不恢复为目标方案的质量或成本证据；具体影响见 [RESULTS.md](./RESULTS.md)。

再次进入模型比较前，先在本地验证：相同普通会话与固定配置下，问答、Worker 反馈、任务板场景的固定 system prompt 和缓存标识一致；加载内容通过当前事件或工具结果追加，不重写既有历史；指南仍在对应处理动作前可见。每日反思是原有独立 profile，不要求与普通主控正文相同。只检查指南“存在”不足以证明装配正确。

上述本地门槛已覆盖并通过，另检查了同一 episode 去重、运行中注入、重启恢复、压缩成功/失败、任务板写入门及后续历史清理。相关测试 741 项，决策测试器 9 项，Docker 检查 11 项通过；后两类验证使用脚本响应，不提供模型质量分数。固定 system 与缓存键通过不等于已测得 Provider 命中率、节省比例或交付质量。新旧模型对比仍需冻结修复后的版本与输入，不复用旧候选输出。

## 结论口径

- 工程装配正确、有限案例决策符合要求、完整任务质量不退步，是三个不同结论。
- 第一阶段只检查决策，不能以派发、选择读取或声明完成冒充真实执行和交付。
- 目前的普通任务退步界限建议为完成率下降 5 个百分点。正式统计验收必须先固定代表性抽样方法、指标、样本量、总预算和区间计算方法；本轮十个选定案例不满足这一条件，不计算泛化通过率，不宣称质量等价。
- 先前“零不利配对约需 59 对”的数值只适用于独立同分布的零事件二项上界示例，约束“旧成功、新失败”的概率；不是通用的两版本完成率差异样本量公式。重复同一道题不能当作新增业务场景。
- 严重越权、虚报完成、破坏已有工作单列；不得用较低成本抵消。一次错误不能自动归因为提示词退化。

## 第零阶段：修复测量干扰

1. 请求预算到顶只拒绝后续新请求，不取消此前已准入的响应；等已准入请求和运行回合收口后清理。仍保留单请求与等待超时，预算不足单独记录。
2. Docker 进程/线程上限从 64 调整为 256，保留无网络、无宿主挂载、普通用户、只读根、256 MiB 内存与 1 CPU。用实际六路 Read 和 cgroup 计数检查，不借修改提示词让模型少并发来绕过夹具问题。
3. 两项修复均先出现定向失败，修复后连同原本地链路共 9 项通过。原模型日志和原比较结果不回写，也不自动补跑原失败。
4. 主控读仅存在 Docker 内的路径、部分记忆 RPC 未实现，仍是旧完整链路装置的已知缺口。在下一阶段正式完整任务比较之前补齐或明确排除，不将这种错误算到提示词质量中。

## 第一阶段：十项有限决策检查

| 案例 | 主要检查 |
| --- | --- |
| 普通翻译 | 准确表达、当前会话交付、不派无用任务 |
| 一次性文件委托 | 目标、顺序、保存位置和不覆盖约束完整传达 |
| 会话不允许派发 | 不以 Worker ready 代替派发权限 |
| 桌面权限不足 | 指明所缺权限，不先派发或绕过 |
| 已授权却重复询问 | 主控沿用有效授权内部续办 |
| 自报完成但缺少一项 | 依据实际覆盖范围判断，补齐缺项 |
| 一次性脚本修复 | 直接处理局部任务，不强加项目初始化 |
| 多环节只读诊断 | 查证原始错误，保留只读边界 |
| 撤销旧规则后的文档 | 不把本次方法升级为新的排他规定 |
| 归档材料分类 | 按用途保留题集、排除日志、保护已有文件 |

完整人工输入和逐项语义标准在 `decision-cases.mjs`。所有案例都是新人工内容；其中三项保留已见历史机制，属于开发回归集，不是未见留出集。不得据此宣称覆盖真实流量分布。

使用实际编译的角色提示词与工具描述，候选提供该角色的 guidance。双方工具描述相同（基线没有新增 guidance 入口），旧正文来自既有冻结基线 `739b50e0`。不还原两个完整生产版本。主控反馈场景为候选提供产品实际会直接提供的反馈指南。

只有静态 guidance、产品权限计算以及明确人工 Worker 观察可返回本地结果。其余工具调用只记录模型的选择，不执行，不返回虚构成功回执；Shell 不执行，消息不外发，Worker 不启动。首次业务选择或普通回答即结束；因此只能判断下一步，不能检查其后完整工作是否完成。若先选择取证，不能把尚未生成的交接判为正确或错误。

### 接收方与用量边界

- 沿用百炼 `https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`，固定 `qwen3.8-max` / OpenAI 兼容格式。默认模型即使改变也不混用，不修改配置。
- 发送范围：实际核心提示词、适用指南、选定工具说明和上述人工案例；不含原始聊天、业务目录、截图或密钥。凭据仅用于该 Provider 的正常鉴权。
- 10 案例 × 2 版本 × 2 次 = 40 条短轨迹、20 对；每条最多 3 次，整批最多 120 次模型请求，每次最大输出 2,400 tokens、90 秒。
- 串行运行。累计已报告输入（含缓存）加输出达到 500,000 tokens 后不再开始新请求；最后一个已开始请求可能使总量超过该阈值。这是用量停止线，不是人民币账单封顶；未报告用量不当作零费用。
- 第一次 Provider 错误即停整批；不重试、不重抽成功结果、不自动换模型、不自动扩样。未开始、缺响应、截断、覆盖缺口、轮次上限分别保留。
- 原始结果仅本机保存，文件权限 0600；正文审阅包不含隐藏推理。无需额外模型裁判调用。

### 判定与匿名审阅

先对每个输出按冻结标准标记“符合”“明确违反”或“证据不足”，引用具体内容；再比较 A/B 的语义表现。工具数、字数、是否读取指南都不能单独代表质量。额外询问、无用安排和范围膨胀作为过程负担单列。

结束时生成随机 A/B 标签的 `review-blinded.json`，映射单独保存在 `review-mapping.json`。人工标准不进入被测模型输入。标签隐藏不保证行为或措辞完全不透露版本；由当前助手自审也不属于独立评审，不能包装成独立盲评。需要人类校准的分歧明确保留。

## 第二阶段：完整任务验收的进入条件

第一阶段用于发现明显问题、决定后续投入，不负责宣布改造胜出。完整任务比较须先处理第零阶段剩余缺口，另外冻结有代表性的完整任务及费用预算；确认样本量是否足以排除约定幅度的退步。失败尝试成本计入总量，比较同时报告交付数量和完整成本。证据不足则保留“不确定”，不无限扩样，也不把第一阶段二十对当成完整任务样本。

第一阶段旧运行结束，实际 55 次请求、224,127 tokens，未超过上述边界；因后续确认的装配缺陷，不记为方案验收完成。原日志、判定和用量不重写。实现修复仅在本地，未合并、推送或部署；修复后的新增模型批次仍须冻结版本、具体范围和预算。
